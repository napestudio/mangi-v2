# Mangiar v2 — Menú

Catálogo de productos y categorías, con precios diferenciados por tipo de pedido. Es CORE (sin módulo propio, siempre disponible) — casi todo otro módulo lo lee (Orders, Inventory, Suppliers, Printing vía categorías/estaciones). Ver `mangiar-architecture`.

## Mapa de archivos

- **Backend**: `apps/api/src/modules/products/` (`products.controller.ts`/`products.service.ts`, `products.module.ts`, `dto/create-product.dto.ts`, `dto/update-product.dto.ts`) + `apps/api/src/modules/categories/` (`categories.controller.ts`/`categories.service.ts`, `categories.module.ts`, `dto/create-category.dto.ts`, `dto/update-category.dto.ts`).
- **Prisma**: `Product`, `ProductPrice` (se borra/recrea en transacción en cada update, no se hace upsert fila-por-fila), `Category`.
- **Shared**: `packages/shared/src/schemas/products.schema.ts`, `packages/shared/src/schemas/categories.schema.ts`; enums `PriceType`, `ProductTag`, `UnitType`, `WeightUnit`, `VolumeUnit`.
- **Frontend**: `apps/app/src/routes/_app/menu/products/index.tsx` — CRUD completo. Alta y detalle de productos viven las dos dentro del mismo `SidePanel` (no hay form inline arriba de la tabla): alta como un `<Wizard>` de 5 pasos (`apps/app/src/components/ui/wizard.tsx`, ver `mangiar-ui-ux`); clickear una fila abre el panel en modo **info** (solo lectura, `ProductInfoView`), con "Editar"/"Eliminar" como acciones separadas — ver bullet de `panelMode` más abajo. Categorías: hay un botón "Categorías" (ícono `FolderOpen`) al lado de "+ Producto" que abre un **segundo `SidePanel` independiente** con listado + alta inline — ver bullet dedicado más abajo.
- **Desktop**: ninguno.

## Decisiones y convenciones

- `ProductPrice` tiene una fila por `PriceType` (`DINE_IN`, `TAKE_AWAY`, `DELIVERY`) — un producto sin precio configurado para el tipo que necesita un pedido (`toPriceType()` en `mangiar-orders`) hace que ese pedido falle con 400 "no tiene precio configurado para X", no que caiga a un precio default silencioso.
- `Category` es compartida entre Menú y Printing (`StationCategory` vincula una categoría a una estación de impresión) — borrar o reestructurar categorías libremente puede romper el agrupamiento de tickets de cocina sin que Menú lo sepa.
- **Combos**: `Product.isCombo` + el join `ProductComponent` (`comboId`/`componentId`/`quantity`) ya están conectados de punta a punta — `CreateProductDto`/`UpdateProductDto` y `createProductSchema`/`updateProductSchema` (en `packages/shared`) aceptan un array `components: { componentId, quantity }[]`, validado tanto en el schema Zod (`.superRefine`: un combo necesita ≥1 componente, no al revés) como server-side en `ProductsService.validateComponents` (no auto-referencia, no combos anidados — un componente no puede ser a su vez `isCombo`). `ProductsService.update()` borra/recrea `ProductComponent` igual que ya hacía con `ProductPrice`. Un combo **mantiene su propio `trackStock`/`stock`** independientemente de sus componentes — no es solo un agregado, puede tener un cupo propio además del de cada producto que lo integra (decisión explícita del usuario).
- Los `ModifierOption`/`ModifierGroup` (modificadores de producto) están modelados en Prisma y se usan en `orders.service.ts` al armar un `OrderItem`, pero no hay una pantalla de gestión de modificadores en este módulo todavía, ni el consumo de stock de ingredientes vía `ModifierOptionIngredient` — quedó explícitamente diferido a una etapa futura (ver `mangiar-inventory` para el estado del descuento de stock en ventas, que sí está implementado para productos/combos).
- **Form de producto simplificado a propósito** (`index.tsx`, pedido explícito del usuario: "simplificar la UI, es confuso mezclar todo"): no tiene campo SKU (el DTO/schema lo siguen aceptando opcionalmente, simplemente esta UI no lo completa). El precio es un único input (mapea a `PriceType.DINE_IN` y, si no está tildado "Precios diferenciados", se manda igual para los 3 `PriceType` al guardar — así un producto sin delivery no necesita tocar nada); tildar "Precios diferenciados" revela los inputs de "Para llevar" y "Delivery" para sobreescribirlos puntualmente. Al editar un producto existente, el form decide si mostrar ese checkbox tildado comparando si los 3 precios guardados son iguales (heurística de sync al abrir el panel, no un campo que se persista).
- **Checkbox "Gratis"**: fuerza los 3 `PriceType` a `0` y deshabilita el input de precio (y oculta "Precios diferenciados", que no tiene sentido si todo es `0`) — pensado para productos de cortesía (ej. pan) que igual necesitan `trackStock` para controlar cuánto queda. No es un campo propio del modelo: al reabrir un producto existente, se re-detecta como "gratis" si **todos** sus precios cargados son `0`. `$0` es un precio válido de punta a punta (`price: z.number().nonnegative()` en el schema Zod ya lo permitía) — este checkbox es pura UX, no requirió cambios de backend.
- El control de stock (`ProductStockSettings`, componente separado) es su propia caja visual con label "Control de stock" — contiene el checkbox `trackStock` y, solo si está tildado, `unitType`/`weightUnit`/`volumeUnit`. En edición se renderiza aparte del `ProductForm` (dentro del mismo `SidePanel`); en el alta vive adentro del paso 4 del wizard ("Precios y stock"), junto a `ProductPricingFields` — se puede activar `trackStock` desde el primer guardado, no hace falta crear el producto primero. **Gateado por `inventoryActive`** (fix 2026): las dos apariciones (`{inventoryActive && <ProductStockSettings .../>}`) no se renderizan si el restaurante no tiene `Module.INVENTORY` activo — antes se mostraba siempre, lo que permitía activar `trackStock`/cargar stock inicial sin tener el módulo comprado (ver `mangiar-inventory`). Ocultarlo no pisa el valor de un producto que ya tenía `trackStock=true` de antes (de cuando el módulo sí estaba activo): `form.trackStock` sigue viviendo en el estado del form aunque el bloque no se renderice, mismo mecanismo ya usado para que `minStock`/`maxStock` sobrevivan sin tener un input en este form.
- **Stock mínimo/máximo deliberadamente fuera de este form** (pedido explícito: "eso es para configurar alertas, ahora no son campos que necesitemos") — `minStock`/`maxStock` siguen existiendo en el modelo/DTOs/schema (nada se borró ahí), simplemente no hay ningún input que los edite todavía. Si un producto ya tenía esos valores cargados (de antes, o por otro camino), `toPayload()` los manda como `undefined` al no haber estado en el form — Prisma trata `undefined` como "no tocar el campo" en un `update`, así que un valor existente sobrevive intacto aunque esta UI no lo muestre. Cuando se retome (alertas de stock bajo/exceso), agregar los inputs de vuelta a `ProductStockSettings` en vez de crear un componente nuevo.
- **"Stock inicial" — solo en el alta, nunca en edición**: el paso 4 del wizard pasa `showInitialStock` a `ProductStockSettings`, que entonces muestra un input extra bajo la unidad, atado a `form.initialStock` (string, no se persiste tal cual — ver `toCreatePayload` abajo). Editar un producto existente NUNCA muestra ese input — ahí el único camino para tocar el stock sigue siendo `StockSection` (con su propio registro de auditoría vía `StockService`), para no tener dos caminos distintos tocando el mismo número. `toCreatePayload(form, isActive)` (separado de `toPayload()`, que sigue usando `updateProduct`) agrega `stock: Number(form.initialStock)` solo si `trackStock` está tildado y el campo no quedó vacío — `CreateProductDto`/`createProductSchema` ganaron un `stock?: number` opcional para esto (`UpdateProductDto` deliberadamente NO lo tiene, para que no se cuele un segundo camino de escritura directa sobre un producto ya existente). Server-side, `ProductsService.create()` ahora inyecta `StockService` (vía `InventoryModule` importado en `ProductsModule`, mismo patrón que `OrdersModule`) y, si vino `stock > 0`, llama `stockService.set(..., { productId, stock, reason: "Stock inicial" })` después de crear el producto — así el valor inicial también queda como un `StockMovement` auditable, no una escritura muda al campo (ver `mangiar-inventory`).
- **Alta de producto = `<Wizard>` de 5 pasos, dentro del `SidePanel`** (antes era un form inline arriba de la tabla — se migró a pedido explícito del usuario: "ya que el form de edición va en el sidebar, usemos lo mismo para el de creación"). Los campos están agrupados en sub-componentes reusados tanto por el wizard (alta) como por `ProductForm` (edición, un solo form plano con todos juntos): `ProductBasicFields` (nombre/descripción/categoría + `isActive` opcional vía prop `showActiveToggle`), `ProductImageField`, `ProductComboFields` (elegir Normal/Combo con dos tarjetas clickeables en vez de un checkbox, y si es Combo el picker de componentes), `ProductPricingFields`, `ProductTagsFields`. Pasos del wizard, en orden: (1) Datos básicos — **sin** el checkbox "Producto activo**"** (`showActiveToggle={false}`, ver bullet de borrador/publicado abajo); (2) Imagen (`optional`); (3) Tipo de producto (Normal/Combo); (4) Precios y stock (`ProductPricingFields` + `ProductStockSettings`); (5) Etiquetas (`optional`) — acá viven los botones finales, no el wizard (ver `mangiar-ui-ux`, el wizard no renderiza un botón de "completar" genérico).
- **"Guardar borrador" / "Guardar y publicar" en vez de un checkbox "Producto activo"** en el alta (pedido explícito): ambos botones llaman a la misma mutación (`createProduct.mutate(isActive: boolean)`), que arma el payload con `toPayload({ ...form, isActive })` — "Guardar borrador" manda `isActive: false`, "Guardar y publicar" manda `isActive: true`. No es un campo nuevo en el modelo, reusa `Product.isActive` que ya existía. La tabla de productos muestra un badge "Borrador" (ámbar) al lado del nombre cuando `!isActive`, para distinguirlo de un producto simplemente desactivado manualmente luego desde edición (donde el checkbox "Producto activo" sigue existiendo sin cambios).
- **Toast al guardar o eliminar un producto**: `useToast().show({message, variant: "success"})` (ver `mangiar-toast`) tras alta ("Producto creado y publicado." / "Producto guardado como borrador.", según el botón) y tras eliminar ("Producto eliminado correctamente."). Editar un producto existente (`updateProduct`) sigue sin toast — no se pidió.
- **Panel de categorías** (botón "Categorías" en `index.tsx`): un `<SidePanel>` separado del de productos (dos instancias de `SidePanel` coexisten en el archivo), con su propio estado (`showCategories`/`categoryForm`) — **solo alta + listado**, no edición ni borrado todavía (no se pidió; el backend de categorías sí soporta CRUD completo, ver `categories.controller.ts`, así que agregar editar/eliminar ahí es extender la UI, no el backend). Mutua exclusión manual entre los dos `SidePanel` (abrir uno cierra el otro) — `openCreate`/`openExisting`/`openCategories` se encargan de eso; si se agrega un tercer panel a esta pantalla, replicar el mismo patrón o vuelven a aparecer dos paneles superpuestos (ambos hacen `createPortal` a `document.body`, no hay guard automático).
- **`panelMode: "info" | "edit"`** gobierna qué se ve dentro del panel de un producto existente (no aplica al alta, que siempre es el wizard). `openExisting(row)` siempre resetea a `"info"` al abrir — clickear una fila nunca entra directo a editar. `"info"` renderiza `ProductInfoView` (solo lectura: estado activo/borrador, imagen, descripción, categoría, todos los precios configurados —no solo el primero—, componentes del combo con cantidad, etiquetas, y stock actual + unidad si `trackStock`) con los 2 botones de acción en el footer fijo ("Editar"/"Eliminar"). "Editar" (`openEdit()`) llama `syncFormFromProduct(selectedProduct)` recién en ese momento — no hay un `useEffect` sincronizando `form` en cada cambio de selección como antes; `form` es pura "scratch" de edición, `"info"` nunca lo lee. "Cancelar" en modo edit vuelve a `"info"` sin pedir nada (en `"info"` no hay nada que revertir porque nunca escribe sobre `form`).
- **Ya no existe un modo "stock" en este panel** (fix 2026, pedido explícito del usuario: mezclar la gestión de un módulo opcional —Inventario— dentro de una pantalla CORE —Menú— era confuso). El botón "Editar stock" y `StockSection` se sacaron de acá por completo; la columna "Stock" de la tabla y el dato en `ProductInfoView` quedan como referencia de solo lectura (ya gateados por `inventoryActive`), pero ajustar el valor pasa a ser exclusivo de `inventory/stock/index.tsx` — ver `mangiar-inventory`.
- **`panel` guarda el id del producto, no una copia de la fila** (`useSidePanel<string>()`, no `<ProductListItem>()`) — `selectedProduct = products?.find(p => p.id === panel.selected)`. Esto es a propósito: así, después de cualquier mutación que invalide `["products"]` (editar, ajustar stock, activar/desactivar), `selectedProduct` se refresca solo en el próximo render sin tener que empujar manualmente la fila actualizada de vuelta al estado del panel. Si se agrega un cuarto modo o una pantalla parecida, mantener este patrón (id + derive) en vez de volver a guardar el objeto completo — guardar el objeto es exactamente lo que causaba que la vista de info mostrara datos viejos después de guardar un cambio.
- **Confirmación antes de eliminar** (ver `CLAUDE.md`): "Eliminar" en el footer de `"info"` no borra directo — pasa por `confirmingDelete` (mismo patrón inline Sí/No que `OrderDetailPanel`). El bloque de confirmación también renderiza `deleteProduct.isError` (vía `extractErrorMessage`, mismo helper duplicado en `orders/new.tsx`/`settings/restaurant.tsx`/`settings/map.tsx`) — **no asumir que un mutate que falla ya se nota solo**: antes de esto, un producto con pedidos asociados tiraba 500 contra una violación de FK y la UI no mostraba nada, así que al usuario le parecía que el botón "Sí, eliminar" no hacía nada. `deleteProduct.reset()` se llama al cerrar el panel, abrir otro producto, o tocar "No" — si no, el mensaje de error de un intento fallido anterior quedaba pegado la próxima vez que se abría la confirmación.
- **No se puede eliminar un producto con pedidos (u otros registros) asociados — a propósito**: `OrderItem.productId` no tiene `onDelete: Cascade` (ni `SetNull`) hacia `Product` — es intencional, para que borrar un producto nunca se lleve puesto el historial de pedidos que lo usaron (necesario para estadísticas, pedido explícito del usuario). `ProductsService.remove()` atrapa el `PrismaClientKnownRequestError` código `P2003` (mismo patrón ya usado en `tables.service.ts` para mesas con reservas) y lo convierte en `ConflictException` (409) con mensaje claro — en vez de dejar que el filtro global devuelva un 500 genérico. Si un producto ya fue vendido alguna vez (o referenciado por un combo/orden de compra/etc.), no se puede hacer hard-delete: la alternativa es desactivarlo (`isActive: false`, mismo checkbox/concepto que "Guardar borrador") para sacarlo del catálogo activo sin romper el historial.

## Limitaciones conocidas

- Panel de categorías sin editar/eliminar (ver arriba) — solo alta + listado de solo lectura.
- No hay gestión de modificadores en la UI ni consumo de stock de ingredientes por modificador (ver arriba) — próxima etapa.
- El componente de combo-picker del form de productos es un `<select>` simple (no el `ProductSearchCombobox` que usan Orders/Salon) — ese combobox está acoplado a `priceType` y pensado para armar un pedido, no para elegir cualquier producto no-combo como ingrediente de un combo.
